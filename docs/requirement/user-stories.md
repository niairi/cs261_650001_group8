## US1 : Login เข้าสู่ระบบด้วย TU Account

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ. หรือเจ้าหน้าที่ภาควิชาฯ ที่มี TU Account
- **I want to :** เข้าสู่ระบบจองห้องด้วย Username และ Password เดียวกับ TU Account
- **So that :** 1) เข้าใช้ระบบได้อย่างปลอดภัยโดยไม่ต้องสมัครสมาชิกใหม่ 2) ระบบแสดงเมนูตามสิทธิ์ของฉัน

**Priority :** High · **Estimate :** 8 points · **Sprint :** Sprint 1

**Pre-conditions**
- ผู้ใช้มี TU Account ที่ Active
- ระบบเชื่อมต่อ TU REST API ได้ (มี Application-Key)

**Post-conditions**
- สร้าง session ของผู้ใช้
- บันทึก/อัปเดตข้อมูลผู้ใช้ (รหัส, ชื่อ, สาขา, อีเมล) ลงตาราง users
- บันทึกเวลา Login

**Definition of Done (Test Cases)**
- **TC1 (สำเร็จ) :** Given บัญชี 6809650069 ที่ Active สาขาวิทยาการคอมพิวเตอร์ → When กรอก Username/Password ถูกต้องแล้วกด Login → Then เข้าหน้าตารางห้อง และมุมขวาบนแสดงชื่อ-นามสกุลของผู้ใช้
- **TC2 (รหัสผ่านผิด) :** Given บัญชี 6809650069 → When กรอก Password ผิด → Then แสดง "Username หรือ Password ไม่ถูกต้อง" และไม่สร้าง session
- **TC3 (กรอกไม่ครบ) :** Given หน้า Login → When เว้นช่อง Password ว่างแล้วกด Login → Then แสดงข้อความให้กรอกให้ครบ และไม่ส่งคำขอไป Backend

> **การเปลี่ยนแปลง (20 ต.ค. 2569, ตัดสินโดย PO):**
> - TC3 เดิม "ไม่ใช่สาขา CS" ย้ายไป Sprint 2 เป็นการ์ด "US1: ตรวจสาขาวิทยาการคอมพิวเตอร์ตอน login" (TU API ตรวจแค่ username/password ไม่ได้กรองสาขา)
> - TC5 เดิม "สิทธิ์ Admin เห็นเมนูจัดการการจอง" ย้ายไปเป็น TC5 ของ US7 (Sprint 2)

## US2 : ดูตารางสถานะห้องว่าง/ไม่ว่าง แบบ Real-time

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ.
- **I want to :** ดูตารางสถานะว่าง/ไม่ว่างของห้อง Co-Working Space แยกตามห้องและช่วงเวลา 09:00–16:00 โดยสถานะอัปเดตเองทันที
- **So that :** ฉันรู้ได้ทันทีว่าห้องไหนว่างช่วงไหน โดยไม่ต้องเดินไปดูที่ห้องเอง

**Priority :** High · **Estimate :** 10 points · **Sprint :** Sprint 1

**Pre-conditions**
- มีข้อมูลห้อง Room A (101), Room B (102), Room C (103) ในระบบ

**Post-conditions**
- ไม่มีการเปลี่ยนแปลงข้อมูล (อ่านข้อมูลอย่างเดียว)

**Definition of Done (Test Cases)**
- **TC1 (แสดงถูกต้อง) :** Given Room A (101) วันที่ 20 ต.ค. 2569 ช่วง 13:00–15:00 ถูกจองแล้ว และ 15:00–16:00 ว่าง → When เปิดตารางวันที่ 20 ต.ค. → Then ช่วง 13:00–15:00 เป็นสีแดง "ไม่ว่าง" และ 15:00–16:00 เป็นสีเขียว "ว่าง"
- **TC2 (Real-time) :** Given ผู้ใช้ A เปิดหน้าตารางค้างไว้ → When ผู้ใช้ B จอง Room A (101) ช่วง 15:00–16:00 สำเร็จ → Then หน้าจอของผู้ใช้ A เปลี่ยนช่องนั้นเป็นสีแดงภายใน 5 วินาทีโดยไม่ต้อง refresh
- **TC3 (ช่วงวันที่แสดง) :** Given วันนี้ 20 ต.ค. 2569 → When เปิดหน้าตาราง Real-time → Then แสดงสถานะของวันนี้ (20 ต.ค.) และพรุ่งนี้ (21 ต.ค.) และเมื่อกดเข้าห้อง แสดงตารางรายสัปดาห์ 20–27 ต.ค.
- **TC4 (โหลดข้อมูลไม่ได้) :** Given Backend ไม่ตอบสนอง → When เปิดหน้าตาราง → Then แสดงข้อความ "ไม่สามารถโหลดข้อมูลสถานะห้องได้ กรุณาลองใหม่อีกครั้ง" และไม่แสดงข้อมูลเก่าเป็นข้อมูลปัจจุบัน
- **TC5 (ห้องปิดใช้งาน) :** Given Room C (103) ถูกตั้ง is_active = FALSE → When เปิดหน้าตาราง → Then ไม่แสดง Room C ในรายการห้อง

## US3 : กดจองพื้นที่และระบุช่วงเวลาล่วงหน้า

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ.
- **I want to :** เลือกห้อง วัน ช่วงเวลา จำนวนคน และวัตถุประสงค์ แล้วกดยืนยันการจองล่วงหน้า
- **So that :** ฉันมั่นใจว่ามีห้องใช้งานตามเวลาที่ต้องการ และไม่ชนกับผู้อื่น

**Priority :** High · **Estimate :** 12 points · **Sprint :** Sprint 1

**Pre-conditions**
- Login แล้ว
- ช่วงเวลาที่เลือกยังว่าง
- เวลาอยู่ในช่วง 09:00–16:00 เป็นเวลาเต็มชั่วโมง (เปลี่ยนจาก 17:00 ใน Sprint 2)
- จองครั้งละไม่เกิน 3 ชม. และจองล่วงหน้าได้ไม่เกิน 7 วัน

**Post-conditions**
- บันทึกการจองในตาราง booking สถานะ BOOKED
- ช่วงเวลานั้นแสดงเป็นไม่ว่างสำหรับผู้ใช้อื่น
- ส่งอีเมลยืนยันการจอง (US5)

**Definition of Done (Test Cases)**
- **TC1 (สำเร็จ) :** Given วันนี้ 20 ต.ค. 2569 · Room A (101) วันที่ 22 ต.ค. ช่วง 10:00–12:00 ว่าง → When เลือกช่วงนี้ จำนวน 3 คน วัตถุประสงค์ "Group Study" แล้วกดยืนยัน → Then แสดง "จองสำเร็จ" พร้อมสรุป Room A / 22 ต.ค. 2569 / 10:00–12:00 และสถานะเป็น BOOKED
- **TC2 (จองซ้อน) :** Given Room A (101) วันที่ 22 ต.ค. ช่วง 10:00–12:00 ถูกผู้อื่นจองแล้ว → When จองช่วง 11:00–13:00 → Then แสดง "ช่วงเวลานี้ถูกจองแล้ว" และไม่บันทึก
- **TC3 (เกิน 3 ชม.) :** Given Room B (102) วันที่ 22 ต.ค. ว่างทั้งวัน → When จองช่วง 09:00–13:00 (4 ชม.) → Then แสดง "จองได้ครั้งละไม่เกิน 3 ชั่วโมง" และไม่บันทึก
- **TC4 (เกิน 7 วัน) :** Given วันนี้ 20 ต.ค. 2569 → When จองวันที่ 28 ต.ค. (ทั้งจากปฏิทินและยิง API ด้วย Postman) → Then ปฏิทินเลือกไม่ได้ และ API ตอบ "จองล่วงหน้าได้ไม่เกิน 7 วัน"
- **TC5 (นอกเวลา) :** Given Room A (101) วันที่ 22 ต.ค. ว่าง → When จองช่วง 16:00–18:00 → Then แสดง "จองได้เฉพาะช่วง 09:00 - 16:00 น." และไม่บันทึก

> **การเปลี่ยนแปลง (Sprint 2, ตกลงในประชุม):** เวลาทำการเปลี่ยนจาก 09:00–17:00 เป็น **09:00–16:00** (แก้โค้ดใน Task64)
- **TC6 (เวลาผ่านแล้ว) :** Given ขณะนั้น 20 ต.ค. 11:30 → When จองช่วง 09:00–10:00 ของวันนี้ → Then แสดง "ไม่สามารถจองเวลาที่ผ่านมาแล้ว" และไม่บันทึก

## US4 : ดูรายการจองของฉัน และกดยกเลิกการจอง

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ.
- **I want to :** ดูรายการจองของตัวเอง และกดยกเลิกการจองที่ยังไม่ถึงเวลา
- **So that :** ฉันคืนสิทธิ์ห้องให้ผู้อื่นได้เมื่อไม่สามารถมาใช้ห้องตามเวลาที่จอง

**Priority :** High · **Estimate :** 6 points · **Sprint :** Sprint 1

**Pre-conditions**
- Login แล้ว
- มีการจองสถานะ "จองแล้ว"
- เหลือเวลาก่อนเวลาเริ่มอย่างน้อย 30 นาที

**Post-conditions**
- สถานะเปลี่ยนเป็น "ยกเลิกแล้ว"
- ช่วงเวลากลับมาว่าง
- บันทึกเวลาที่ยกเลิก
- ส่งอีเมลแจ้งการยกเลิก (US5)

**Definition of Done (Test Cases)**
- **TC1 (แสดงรายการ) :** Given ผู้ใช้ 6809650069 มีการจอง 2 รายการ → When เปิดหน้า "การจองของฉัน" → Then แสดงเฉพาะรายการของตัวเองครบ 2 รายการ เรียงตามวันและเวลา
- **TC2 (ยกเลิกสำเร็จ) :** Given มีการจอง Room A (101) วันที่ 22 ต.ค. 10:00–12:00 และขณะนั้น 21 ต.ค. 18:00 → When กด "ยกเลิกการจอง" แล้วยืนยัน → Then สถานะเป็น "ยกเลิกแล้ว" และช่วงเวลาในตารางกลับเป็นสีเขียว
- **TC3 (เปลี่ยนใจ) :** Given หน้าต่างยืนยันการยกเลิกแสดงอยู่ → When กด "ไม่ยกเลิก" → Then สถานะการจองไม่เปลี่ยน
- **TC4 (เลยกำหนด) :** Given การจองเริ่ม 22 ต.ค. 10:00 และขณะนั้น 09:45 → When เปิดรายการ → Then ปุ่มยกเลิกกดไม่ได้ และแสดง "ยกเลิกได้ก่อนเวลาเริ่มอย่างน้อย 30 นาที"
- **TC5 (การจองของคนอื่น) :** Given การจองหมายเลขหนึ่งเป็นของผู้ใช้อื่น → When ส่งคำขอยกเลิก → Then ระบบปฏิเสธ (403) และสถานะไม่เปลี่ยน

## US5 : ส่งอีเมลแจ้งเตือนยืนยันการจอง

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ. ที่ทำการจอง
- **I want to :** ได้รับอีเมลยืนยันเมื่อจองหรือยกเลิกสำเร็จ โดยระบุห้อง วัน และเวลา
- **So that :** ฉันมีหลักฐานอ้างอิงและมีข้อความเตือนความจำ

**Priority :** Normal · **Estimate :** 5 points · **Sprint :** Sprint 1

**Pre-conditions**
- การจองหรือการยกเลิกสำเร็จ
- ผู้ใช้มีอีเมล @dome.tu.ac.th จากข้อมูล TU Account

**Post-conditions**
- อีเมลถูกส่ง
- บันทึกผลการส่ง (สำเร็จ/ล้มเหลว) และเวลาส่ง

**Definition of Done (Test Cases)**
- **TC1 (ยืนยันการจอง) :** Given ผู้ใช้จอง Room A (101) วันที่ 22 ต.ค. 10:00–12:00 สำเร็จ → When ระบบบันทึกเสร็จ → Then ภายใน 1 นาที อีเมล @dome.tu.ac.th ของผู้ใช้ได้รับหัวข้อ "[CS Co-Working] ยืนยันการจอง Room A (101) 22/10/2569 10:00–12:00"
- **TC2 (แจ้งการยกเลิก) :** Given ผู้ใช้ยกเลิกการจองข้างต้น → When ยกเลิกสำเร็จ → Then ได้รับอีเมลหัวข้อ "[CS Co-Working] ยกเลิกการจอง…" พร้อมรายละเอียดเดียวกัน
- **TC3 (ส่งไม่ได้) :** Given เซิร์ฟเวอร์อีเมลใช้งานไม่ได้ → When จองสำเร็จ → Then การจองยังถูกบันทึก และบันทึกผลว่าส่งล้มเหลว (status = FAILED ใน email_logs)

> **การเปลี่ยนแปลง (20 ต.ค. 2569, ตัดสินโดย PO):** ข้อความแจ้งบนหน้าจอ "จองสำเร็จ แต่ส่งอีเมลยืนยันไม่สำเร็จ" ย้ายไป Sprint 2

## US6 : แก้ไขเวลาการจองที่ได้จองไปแล้ว

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ.
- **I want to :** เปลี่ยนห้องหรือช่วงเวลาการจองโดยไม่ต้องยกเลิกแล้วจองใหม่
- **So that :** ฉันปรับแผนได้สะดวก และไม่เสียช่วงเวลาเดิมจนกว่าช่วงใหม่จะยืนยันแล้ว

**Priority :** Normal · **Estimate :** 6 points · **Sprint :** Sprint 2 · **Use Case :** UC3

**Pre-conditions**
- มีการจองสถานะ BOOKED ของตัวเอง
- เหลือเวลาก่อนเริ่มอย่างน้อย 30 นาที
- ช่วงเวลาใหม่ผ่านกฎเดียวกับการจอง (US3): ว่าง, อยู่ในเวลาเปิดให้จอง, ครั้งละไม่เกิน 3 ชม., ไม่เกิน 7 วันข้างหน้า, ไม่ใช่เวลาที่ผ่านไปแล้ว

**Post-conditions**
- บันทึกเวลาใหม่ในการจองเดิม (หมายเลขการจองเดิม)
- ช่วงเวลาเดิมกลับมาว่างทันที
- ส่งอีเมลแจ้งการเปลี่ยนแปลง

**Definition of Done (Test Cases)**
- **TC1 (สำเร็จ) :** Given จอง Room A (101) วันที่ 22 ต.ค. 10:00–12:00 ไว้ และช่วง 13:00–15:00 ว่าง → When แก้เป็น 13:00–15:00 → Then บันทึกเวลาใหม่ ช่วง 10:00–12:00 กลับมาว่าง และได้รับอีเมลแจ้งการเปลี่ยนแปลง
- **TC2 (ช่วงใหม่ไม่ว่าง) :** Given Room A (101) วันที่ 22 ต.ค. 13:00–14:00 ถูกผู้อื่นจองแล้ว → When แก้การจองของตนเป็น 13:00–15:00 แล้วกดบันทึก → Then แสดง "ช่วงเวลานี้ถูกจองแล้ว" และการจองเดิม 10:00–12:00 ยังอยู่
- **TC3 (เกิน 3 ชม.) :** Given จอง 10:00–12:00 ไว้ → When แก้เป็น 11:00–15:00 (4 ชม.) → Then แสดง "จองได้ครั้งละไม่เกิน 3 ชั่วโมง" และการจองเดิมไม่เปลี่ยน
- **TC4 (เลยกำหนด) :** Given การจองเริ่ม 10:00 และขณะนั้น 09:45 → When เปิดหน้าการจองของฉัน → Then ปุ่มแก้ไขกดไม่ได้ และถ้ายิง API ตรง ระบบตอบ "แก้ไขได้ก่อนเวลาเริ่มอย่างน้อย 30 นาที"

> PO ปรับจากการ์ด: เพิ่มข้อมูลจริงใน TC2 และการตรวจฝั่ง API ใน TC4 · TC3 ใช้ 11:00–15:00 ซึ่งเกิน 3 ชม. แต่อยู่ในเวลาทำการ 09:00–16:00 จึงทดสอบกฎ 3 ชม. ได้ตรงๆ

## US8 : กดยืนยันการเข้าใช้งาน (Check-in) เมื่ออยู่ภายในระยะ 5 เมตรจากห้อง

- **As a :** นักศึกษาสาขาวิทยาการคอมพิวเตอร์ มธ. ที่จองห้องไว้
- **I want to :** กดยืนยันการเข้าใช้งานผ่านหน้าเว็บเมื่ออยู่ภายในระยะ 5 เมตรจากห้องที่จอง โดยระบบตรวจจากตำแหน่ง (GPS) ของอุปกรณ์
- **So that :** ระบบยืนยันได้ว่าฉันอยู่ที่ห้องจริง และไม่ถูกนับเป็น No-show

**Priority :** Normal · **Estimate :** 10 points · **Sprint :** Sprint 2 · **Use Case :** UC5

**Pre-conditions**
- Login แล้ว และมีการจองสถานะ BOOKED ของห้องนั้นในวันปัจจุบัน
- ผู้ใช้อนุญาตให้หน้าเว็บเข้าถึงตำแหน่ง (Location)
- อยู่ในช่วง 10 นาทีก่อนเวลาเริ่ม ถึง 15 นาทีหลังเวลาเริ่ม

**Post-conditions**
- สถานะการจองเปลี่ยนเป็น CONFIRMED และบันทึก confirmed_at
- การจองที่ CONFIRMED แล้วยกเลิกและแก้ไขไม่ได้

**Definition of Done (Test Cases)**
- **TC1 (สำเร็จ) :** Given จอง Room A (101) เวลา 10:00 และผู้ใช้อยู่ห่างห้อง 3 เมตร → When กด "ยืนยันการเข้าใช้งาน" เวลา 10:05 → Then แสดง "ยืนยันการเข้าใช้งานสำเร็จ" และสถานะเป็น CONFIRMED
- **TC2 (อยู่นอกระยะ) :** Given ผู้ใช้อยู่ห่างห้อง 50 เมตร → When กดยืนยันเวลา 10:05 → Then แสดง "คุณอยู่นอกระยะ 5 เมตรจากห้องที่จอง" และสถานะยังเป็น BOOKED
- **TC3 (ไม่อนุญาตตำแหน่ง) :** Given ผู้ใช้ปฏิเสธการเข้าถึงตำแหน่ง → When กดยืนยัน → Then แสดง "กรุณาอนุญาตการเข้าถึงตำแหน่งเพื่อยืนยันการเข้าใช้งาน" และสถานะไม่เปลี่ยน
- **TC4 (เลยเวลา) :** Given จองเวลา 10:00 และไม่ได้ Check-in → When เปิดหน้าการจองเวลา 10:20 → Then ปุ่มยืนยันกดไม่ได้ แสดง "เลยเวลายืนยันการเข้าใช้งานแล้ว" และสถานะเป็น EXPIRED (ระบบ No-show ของ US9 เปลี่ยนไว้ตั้งแต่ 10:15)
- **TC5 (ก่อนเวลา) :** Given จองเวลา 10:00 → When กดยืนยันเวลา 09:40 → Then แสดง "ยืนยันการเข้าใช้งานได้ตั้งแต่ 09:50" และสถานะยังเป็น BOOKED

> PO เพิ่ม TC5 (ก่อนเวลา) และปรับ TC4 ให้สอดคล้องกับ US9 · หมายเหตุความเสี่ยง: GPS ในอาคารอาจคลาดเคลื่อนเกิน 5 เมตร ต้องทดสอบที่ห้องจริง ถ้าไม่แม่นพอ PO จะพิจารณาเพิ่มวิธีสำรอง (เช่น QR Code หน้าห้อง) ใน Sprint ถัดไป

- Scheduler ของระบบทำงานอยู่ (ตรวจทุก 1 นาที)

**Post-conditions**
- สถานะเป็น EXPIRED (No-show)
- จำนวน No-show ของผู้ใช้ในภาคการศึกษานี้ +1
- ช่วงเวลาที่เหลือตั้งแต่ชั่วโมงเต็มถัดไปกลับมาว่าง

**Definition of Done (Test Cases)**
- **TC1 (ไม่ Check-in) :** Given 6809650069 จอง Room A (101) 10:00–12:00 และไม่ Check-in → When ถึงเวลา 10:15 → Then สถานะเป็น EXPIRED (No-show) จำนวน No-show เป็น 1 และช่วง 11:00–12:00 กลับมาว่างในตาราง
- **TC2 (Check-in แล้ว) :** Given Check-in เวลา 10:05 → When ถึงเวลา 10:15 → Then สถานะยังเป็น CONFIRMED และจำนวน No-show ไม่เพิ่ม
- **TC3 (ยกเลิกตามกำหนด) :** Given ยกเลิกเวลา 09:00 (ก่อนเริ่ม 30 นาทีขึ้นไป) → When ถึงเวลา 10:15 → Then สถานะยังเป็น CANCELLED และไม่นับเป็น No-show
- **TC4 (ดูจำนวนของตัวเอง) :** Given ผู้ใช้มี No-show 1 ครั้ง → When เปิดหน้าการจองของฉัน → Then แสดง "No-show ภาคการศึกษานี้: 1 / 3 ครั้ง"

> PO เพิ่ม TC4 ตาม Task67 ("API ให้ผู้ใช้ดูจำนวน No-show ของตัวเอง") และระบุว่าคืนเวลาตั้งแต่ชั่วโมงเต็มถัดไป

## US10 : ระบบแบน (Blacklist) 30 วันเมื่อ No-show ครบ 3 ครั้ง

- **As a :** เจ้าหน้าที่ภาควิชาฯ
- **I want to :** ให้ระบบระงับสิทธิ์การจองของนักศึกษาที่ No-show ครบ 3 ครั้งในภาคการศึกษาเป็นเวลา 30 วันโดยอัตโนมัติ
- **So that :** มีการบังคับใช้กฎอย่างเท่าเทียมและลดการจองทิ้งไว้

**Priority :** Normal · **Estimate :** 6 points · **Sprint :** Sprint 2 · **Use Case :** UC5

**Pre-conditions**
- ผู้ใช้มี No-show 2 ครั้งในภาคการศึกษาปัจจุบัน

**Post-conditions**
- ผู้ใช้ถูกบันทึกใน Blacklist พร้อมวันสิ้นสุด
- ส่งอีเมลแจ้งการระงับสิทธิ์
- การจองอื่นที่จองไว้ล่วงหน้าแล้ว**ยังอยู่** (ไม่ยกเลิกอัตโนมัติ)

**Definition of Done (Test Cases)**
- **TC1 (ครบ 3 ครั้ง) :** Given 6809650069 มี No-show 2 ครั้ง → When เกิด No-show ครั้งที่ 3 วันที่ 22 ต.ค. 2569 → Then ถูกระงับสิทธิ์ถึงสิ้นวันที่ 21 พ.ย. 2569 และได้รับอีเมลแจ้ง
- **TC2 (ถูกระงับแล้วพยายามจอง) :** Given ผู้ใช้ถูกระงับสิทธิ์ถึง 21 พ.ย. 2569 → When พยายามจอง (ทั้งหน้าเว็บและยิง API ตรง) → Then แสดง "คุณถูกระงับสิทธิ์การจองถึงวันที่ 21 พ.ย. 2569" และไม่บันทึก
- **TC3 (พ้นกำหนด) :** Given วันนี้ 22 พ.ย. 2569 (พ้นกำหนดแล้ว) → When จองใหม่ → Then จองได้ตามปกติ
- **TC4 (ยังไม่ครบ) :** Given มี No-show 2 ครั้ง → When จอง → Then ยังจองได้ตามปกติ

> PO ระบุวันสิ้นสุดให้ชัด ("ถึงสิ้นวันที่") เพิ่มการตรวจฝั่ง API ใน TC2 และกำหนดว่าการจองเดิมไม่ถูกยกเลิก

## US11 : Logout ออกจากระบบ

- **As a :** ผู้ใช้ระบบ (นักศึกษา / เจ้าหน้าที่ภาควิชาฯ)
- **I want to :** ออกจากระบบเมื่อใช้งานเสร็จ
- **So that :** ผู้อื่นที่ใช้เครื่องต่อจากฉันไม่สามารถเข้าบัญชีของฉันได้

**Priority :** Normal · **Estimate :** 2 points · **Sprint :** Sprint 2 · **Use Case :** UC1

- Login อยู่

**Post-conditions**
- token และข้อมูลผู้ใช้ถูกลบออกจากเบราว์เซอร์

**Definition of Done (Test Cases)**
